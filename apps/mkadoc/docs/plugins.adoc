= Writing mkadoc plugins

This guide is for authors of mkadoc plugins.
You receive a **plugin host** in each hook — that is the only API you call.
Canonical types live in the `@mkadoc/plugin-host` package (`MkadocPluginHost`, `MkadocPluginFactory`).

Plugins are enabled from config by **locator**:

* `mkadoc:<name>` — built-in factories shipped with mkadoc (allow-listed)
* `file:./path/to/plugin` (or `./path`, absolute paths) — **external** local-folder plugins (installed into `.mkadoc/plugins/` on first use)
* registry specs (`name@range`), `git:…`, `github:user/repo`, `https://…` tarballs — accepted by the config schema, not implemented yet

Use the builtins under `src/builtins/` as reference implementations, and
`apps/mkadoc-plugin-kroki` as the reference *external* plugin.

== What you can extend

[cols="1,3"]
|===
| Extension point | How

| Rendering a markup format | A **renderer** plugin (`kind: 'renderer'`) with `extensions`, `extractMeta`, `render`, `renderFragment`, `extractFirstLink` (see <<Renderers>>)
| Cross-format capabilities | `provide(name, providerFactory)` / declare them as deps in `host.plugin([...])` (see <<Dependencies>>)
| Generated CSS / JS on every page | Write files under `host.config.output`, then `contributeHead({ links, scripts })`
| UI below the site topbar | `contributeChromeBody(html)` — HTML appended below the topbar, in plugin load order
| Rebuild sensitivity | `registerSiteWideDep` (rebuild every page), `registerClassifier` (force **full**), or `registerAssetPrefix` (**assets** mode)
| Health checks | `check(host)` → `{ ok, message? }` for `mkadoc check`
| On-disk cache | `cacheDir(name)` under `.mkadoc/`
|===

[[Renderers]]
=== Renderers

A renderer is a plugin with `kind: 'renderer'`:

[source,js]
----
export default function myRenderer(options = {}, host) {
  return host.plugin([], () => ({
    name: 'my',
    kind: 'renderer',
    extensions: ['.xyz'],

    // → { title, navLabel } from a page (navLabel = :nav_label: / nav_label)
    async extractMeta(sourceText, absPath) { ... },

    // → { html, title, lang, bodyClass, head, assets, includes }
    // html is the article body; core wraps it into the full page.
    async render({ sourceText, absPath, baseDir }) { ... },

    // render a small markup fragment (used by mkadoc:nav for _nav.adoc files)
    async renderFragment({ sourceText, absPath, baseDir, linkPrefix }) { ... },

    // → { href, label } | null — the first link in a nav fragment
    // (used by mkadoc:nav to derive a source's tab from _nav.adoc)
    async extractFirstLink({ sourceText, absPath, baseDir, linkPrefix }) { ... },
  }))
}
----

Renderers are auto-loaded (`mkadoc:asciidoc`, `mkadoc:markdown`); listing one
under `plugins:` only passes it options. Core discovers pages by asking each
renderer's `extensions`, dispatches page → renderer, and owns page assembly
(wrapper, theme CSS, chrome, head tags).

[[Dependencies]]
=== Dependencies (dependency injection)

Plugins share capabilities through **one flat registry** of names. Core seeds
it with an explicit **module whitelist** (`zod`, `yaml` — the only modules
exposed to plugins, anchored at mkadoc for a single shared instance). Plugins
add to it with `host.provide(name, providerFactory)`; consumers declare what
they need with `host.plugin(deps, create)` and the loader injects the resolved
values **positionally, in declared order**:

[source,js]
----
// provider (e.g. mkadoc:shiki) — factory phase, declaration only. The
// container runs `provider` (once, lazily) when a consumer depends on it.
host.provide('syntax-highlight', async () => {
  const highlighter = await createHighlighter({ themes: [theme], langs })
  return {
    highlight(code, lang) { return highlighter.codeToHtml(code, { lang, theme }) },
  }
})

// consumer (any renderer) — the injected value closes over `syntaxHighlight`
return host.plugin(['syntax-highlight?'], (syntaxHighlight) => ({
  name: 'my-renderer',
  render({ sourceText }) {
    // syntaxHighlight is the resolved value (or undefined when absent)
    // — no lookup at render time, the closure captured it
  },
}))
----

* **The dep list is a name list.** A trailing `?` marks the dependency
  optional: it resolves to `undefined` when no provider is loaded (e.g.
  `'syntax-highlight?'` — degrade to plain listings). A non-optional name with
  no provider fails the load, listing **every** missing dependency at once.
* **`provide` is a declaration, not a value.** The container decides when to
  run provider factories (after all plugins declare, in dependency order,
  `Promise.all`-ed), so construction order never depends on config order.
  `provide` is **factory-phase only** — it throws afterwards, because the
  graph must be fixed before resolution.
* **The registry is session-scoped.** Under `serve`, rebuilds share one
  registry (see xref:../src/session.js[src/session.js]): a provider runs **at
  most once per session** while its `opts.key` is unchanged — pass a key that
  captures everything the value depends on (e.g. shiki uses
  `theme\0langs`), and an `opts.onRelease` that disposes the value when it is
  replaced (key change) or the provider leaves config. Without a key, every
  rebuild re-runs the provider.
* **`host.plugin` is factory-phase only too**, and `create` runs in *config
  order* with all values ready — so chrome order (load order) is preserved
  regardless of the dependency graph.
* **Option parsing stays in the factory** (before deps resolve): use
  `host.import('zod')` there, or import zod directly in builtins. The injected
  values are for the plugin body (`create`), not the factory.
* **Duplicate providers for the same name are a load error** naming both
  owners; core whitelist names (`zod`, `yaml`) are reserved — a plugin cannot
  shadow them. Service names are lowercase-hyphenated **capability nouns**
  describing the interface, never the implementation or package name:
  `syntax-highlight` ✓, `shiki` ✗. Well-known names are listed in
  xref:plugins.adoc[this guide]; check it before picking a name.

=== Runtime services (escape hatch)

Some values cannot exist at load time — they are derived *during* the build.
`mkadoc:nav` publishes `site-root` at chrome time (from the first `_nav.adoc`
link). For those, the legacy runtime pair remains:

[source,js]
----
// provider (at chrome time)
host.provideService('site-root', { href: first?.href ?? null })

// consumer (core's dev server, after chrome)
const root = host.getService('site-root')  // only callable after setup — never during load
----

`getService` throws during plugin load/creation — the registry is incomplete
until every plugin finished setup. Prefer injected deps for anything that is
knowable at load time; keep `provideService`/`getService` for build-time
values only.

== What you cannot extend (core-owned)

* **Topbar / logo / brand** — the topbar is the built-in `mkadoc:topbar` plugin (first in config order so it renders above everything else). The brand comes from `site.brand`. Everything below the topbar comes from plugins via `host.contributeChromeBody` (the built-in `mkadoc:nav` is the reference implementation).
* **Page assembly** — core wraps every renderer's article body into the full HTML document (wrapper, default theme CSS, chrome, head tags). Site authors override the *default theme* with `_theme/theme.css`, and *topbar styles* with the first source's `_theme/topbar.css` (mkadoc:topbar appends it after package defaults).
* **Page HTML body** — the article is the owning renderer's output. `contributeChromeBody` is only for shared site UI that appears on every page (for example a left sidebar), not for the article itself.
* **Config schema / CLI / unknown locators** — plugins are registered via known `mkadoc:*` locators or valid package specs (`npm-package-arg` grammar); factory options you validate yourself.
* **Build orchestration** — core decides `full` / `incremental` / `assets` / `noop` and assembles the shared page chrome/head. You only influence rebuilds via `registerSiteWideDep` / `registerClassifier` / `registerAssetPrefix` (see below). You do not take over writing the topbar/header HTML or flushing head tags — use `contributeChromeBody` and `contributeHead` instead.

== Plugin shape

Export a factory: `(options, host) => declaration` (may be async).

Validate `options` in the factory (Zod + `parsePluginOptions`). Reject unknown keys.
Declare capabilities with `host.provide` and dependencies with `host.plugin`.
The factory returns whatever `host.plugin(deps, create)` returns; the loader
calls `create` with the resolved values and gets your plugin. (A legacy plugin
may still return the plugin object directly; `requires`/`provideService` are
honored for those.)

Return:

[cols="1,3"]
|===
| Field | Purpose

| `name` | Short id (e.g. `nav`)
| `requires` | Optional `string[]` of *runtime* service names this plugin hard-depends on (legacy; verified after load). Load-time capabilities are declared as deps in `host.plugin([...])` instead.
| `setup(host)` | Optional. Runs once after the plugin is created, **before** rebuild mode is decided. Register extensions, classifiers, asset prefixes here. `getService` is **not** available yet — it throws.
| `contributeChrome(host, ctx)` | Optional. Runs each build after mode is known (not called for `noop`). Emit CSS/JS/HTML. `ctx`: `{ mode, pages, paths }` (`mode` is `full` \| `incremental` \| `assets`).
| `check(host)` | Optional. Used by `mkadoc check` only. Keep it cheap.
| `dispose(host)` | Optional. Called when the plugin is unloaded — currently when the `plugins` config changes under `serve`. Release module-level resources (e.g. shiki's highlighter).
|===

Lifecycle order that matters to you:

. Your factory runs — options validated, `host.provide` + `host.plugin` declarations collected. `getService` is **not** available.
. All factories have run — the container resolves every declared dependency (coverage check, then provider factories), then calls each `create(...)` in config order. Injected values are plain closure variables from here on.
. `setup(host)` — classifiers / prefixes must be registered here to affect this build's mode. Still no `getService`; legacy `requires` + `provideService` work here.
. All plugins have loaded — `getService` becomes resolvable, `requires` is verified.
. Core decides `full` / `incremental` / `assets` / `noop`.
. `contributeChrome(host, ctx)` — skipped entirely for `noop`; skip heavy work when `ctx.mode === 'assets'` if you only care about HTML chrome.
. Pages convert (renderers apply their own defaults — e.g. `icons: font` — plus any per-call options like `linkPrefix`).
. A later rebuild with a different `plugins` config (serve) calls `dispose(host)` on the previous set.

== Plugin host API

Every hook receives the same host object.

=== Context

`host.config`:: Resolved project config (`sources`, `output`, `plugins`, …).
`host.root`:: Absolute project root. Join with relative paths from config.

=== Core modules and dependencies

`host.import(specifier)`::
Resolve a module from **mkadoc's core whitelist** (single shared instance).
Only whitelist names resolve — `zod` and `yaml` today; the whitelist is
curated deliberately, and every entry is drift-checked against mkadoc's
`package.json`. Use it for factory-time needs (option parsing) that run before
deps resolve: `const { z } = await host.import('zod')`. Plugin-provided
capabilities are injected via `host.plugin([...])`, never imported.

`host.provide(name, providerFactory, opts?)`::
Declare a load-time capability. `providerFactory` is called (at most once per
session) when a consumer depends on `name`; may be async. Factory-phase only;
duplicate names and whitelist collisions are load errors. Convention: the name
is a lowercase-hyphenated capability noun (`syntax-highlight`, `diagram`).
`opts.key` is the session cache identity — re-providing with the same key
across rebuilds (serve) retains the memoized value, so expensive construction
(e.g. shiki's highlighter) happens once per session; `opts.onRelease` runs
when the value is replaced or the provider is removed from config.

`host.plugin(deps, create)`::
Declare dependencies and your plugin body. `deps` is an array of registry
names (`'name?'` = optional); `create` receives the resolved values
positionally, in declared order, and returns the plugin object. The loader
runs it in config order after all dependencies resolve. Factory-phase only.

=== Head assets

`host.contributeHead({ links?, scripts? })`::
Queue `<link>` / `<script>` tags that core injects into **every page’s** `<head>`.

* `links` — objects like `{ rel: 'stylesheet', href: '/styles/my.css' }`
* `scripts` — objects like `{ src: '/styles/my.js', defer: true }`

Convention: write the file under `output/` yourself (see `resolveSiteAsset` / `writeIfChanged` in existing builtins), use a **root-absolute** `href`/`src` (e.g. `/styles/nav.css`).

=== Below-topbar chrome

Core always emits:

----
<header id="mkadoc-topbar" class="mkadoc-topbar">…</header>
<!-- plugin chrome fragments follow, in plugin load order -->
----

`host.contributeChromeBody(html)`::
Append a HTML fragment below the topbar. Fragments from multiple plugins are concatenated in **plugin load order** (config key order) — each plugin owns its own element (e.g. `<nav class="mkadoc-sources">`, `<aside id="…">`).

Own your markup and CSS. Typical pattern for a fixed side column (e.g. sidebar):

* Contribute an `<aside id="…">` (stable id).
* Ship CSS that positions it (often `position: fixed`) and adjusts `body` padding with `:has(#your-id)`.
* Do not assume another plugin’s fragment exists unless you document that dependency.

The article itself stays in the normal page body from the owning renderer.
See xref:chrome-design.adoc[Site chrome design] for why.

=== Rebuild hints

When files change under `serve`, core chooses a rebuild mode. These two APIs are how you nudge that choice:

`host.registerSiteWideDep(relPath)`::
“If this path changed, rebuild **every** live page (incremental).”  
Use when your chrome is baked into every page’s HTML (same idea as a virtual include for the whole site). Register in `setup`. Example: `mkadoc:nav` registers each source’s `_nav.adoc` and `_nav.yaml`.

`host.registerClassifier(fn)`::
“If this path changed, rebuild **everything** (true full mode).”  
`fn(relPath)` returns `'full'`, or `null`/`undefined` to leave the decision to core/other plugins.  
Register in `setup`. Prefer `registerSiteWideDep` when reconverting all pages is enough; reserve classifiers for orchestration-level changes.

`host.registerAssetPrefix(prefix)`::
“Changes under this path are **styles/assets only** — don’t reconvert AsciiDoc pages.”  
Pass a repo-relative output prefix (the host normalizes a trailing `/`).  
Example: `mkadoc:shiki` registers the directory of its generated CSS so a CSS-only edit can stay in **assets** mode.

=== Filesystem helpers

`host.ensureDir(relOrAbs)`:: Ensure a directory exists; returns absolute path.
`host.cacheDir(name)`:: Ensure `.mkadoc/<name>/` under the project; returns absolute path.
`host.relToRoot(p)`:: Normalize a path to repo-relative form.

== Conventions

=== Locator and options

* Built-in locators: `mkadoc:<name>` (allow-listed in `src/plugin/locators.js`).
* External locators: `file:./path`, `./path`, or absolute paths — parsed with
  `npm-package-arg` (the same spec grammar pacote/npm use). Relative paths resolve
  against the project root.
* External plugins are installed into `.mkadoc/plugins/<name>/` on first load:
  source is copied (fingerprinted — edits re-copy), runtime deps materialized with
  arborist (`ignoreScripts`, `--omit=dev`, cache under `.mkadoc/cache`), entry
  resolved from `package.json` `main`/`exports` else `index.js`.
* Enable in config as `plugins: { "file:./plugins/you": { … } }`.
* Validate options in the factory; shared libraries come from the core
  whitelist (`host.import('zod')` at factory time, `host.plugin(['zod'], ...)`
  in the body) instead of being declared as plugin deps. Do not scrape undeclared
  keys from `host.config.plugins` inside hooks.

=== Assets

* Prefer `/styles/<plugin>.css` (and `.js` if needed) under `output/`.
* Ship plugin assets under your own paths (e.g. `/styles/my.css`); the builtins own `/styles/topbar.*` and `/styles/nav.css`. Site-level topbar CSS tweaks go in the first source’s `_theme/topbar.css` (read by `mkadoc:topbar`).
* Root-absolute URLs in `contributeHead` (leading `/`).

=== Source-tree conventions (site authors)

These are site conventions your plugin may *read*; they are not host APIs:

* First source's `_theme/topbar.css` — optional CSS overrides for **topbar** styles (read by `mkadoc:topbar`; not your job unless you document a parallel file). Only the **first** source's `_theme/` is read at all — the site has exactly one theme.css/topbar.css/nav.css output. A non-first source's `_theme/` is ignored entirely (under serve it is not even watched).
* First source's `_theme/nav.css` — optional CSS overrides for **nav/sidebar** styles (read by `mkadoc:nav`).
* First source's `_theme/theme.css` — optional global overrides appended after the default theme.
* Per-source `_nav.adoc` (rich markup) or `_nav.yaml` (declarative) — used by `mkadoc:nav` for link lists. No other nav formats are supported. With **no** `_nav` file, `mkadoc:nav` falls back to a convention-based **auto-nav**:
+
* folders build the parent/child hierarchy, ordered by file name (natural sort);
* a folder's own page is its `index.<ext>` (clickable); a folder without one is a non-clickable section labelled with its basename;
* a leaf page's label is `:nav_label:` → title → basename.
+
`_nav.yaml` entries are one of:
+
* `page` — link to a page (source-relative, normalized to `.html`); the label comes from the page's title, with an optional `label` as fallback when the page has no title.
* `page` + `children` — a clickable parent (label from its page) with a nested list.
* `label` + `children` — a non-clickable section header.
* `label` + `href` — a raw/external link.
+
----
- page: index
- page: guide
  children:
    - page: guide/setup
- label: Reference
  children:
    - page: plugins
- label: GitHub
  href: https://github.com/xiaoyvr/mkadoc
----
* Files starting with `_` are partials (not pages). Article `include::` edges are tracked in the core dependency graph (`.mkadoc/deps.json`); editing an included partial rebuilds only the pages that include it. Site-wide deps (`index.*`, logo overrides, `_nav.adoc`/`_nav.yaml` via `registerSiteWideDep`) rebuild every page. `_theme/*.css` is CSS-only (assets mode). An unused partial with no known dependents is **`noop`**. Config still forces a **full** rebuild.

=== `contributeChrome` modes

* `full` / `incremental` — update chrome HTML and CSS as needed.
* `assets` — usually skip HTML chrome regeneration. If your only job is a stylesheet derived from config, you may still rewrite CSS here when appropriate.
* `noop` — core does not call `contributeChrome` (nothing to do).

=== Composition with other plugins

* Chrome-body fragments are concatenated; use distinct element ids/classes.
* Layout conflicts (two plugins both claiming full width under the topbar) are resolved by CSS and documentation, not by the host.
* There is no sidebar-specific host API — only `contributeChromeBody`.

== Minimal sketch
[source,js]
----
export default async function myPlugin(raw = {}, host) {
  const { z } = await host.import('zod')          // factory-time options parsing
  const OptionsSchema = z.object({}).strict()
  const options = OptionsSchema.parse(raw)

  host.provide('my-flag', () => ({ value: true })) // load-time capability (optional)

  return host.plugin(['syntax-highlight?'], (syntaxHighlight) => ({
    name: 'my',

    async setup(host) {
      host.registerSiteWideDep('docs/_my.adoc')
     // or, for true full rebuilds only:
     // host.registerClassifier((p) => (p.endsWith('/_my.adoc') ? 'full' : null))
    },

    async contributeChrome(host, { mode }) {
      if (mode === 'assets') return
      // write /styles/my.css under host.config.output …
      host.contributeHead({ links: [{ rel: 'stylesheet', href: '/styles/my.css' }] })
      host.contributeChromeBody('<aside id="mkadoc-my" class="mkadoc-my">…</aside>')
    },

    async check(host) {
      return { ok: true, message: 'my ok' }
    },
  }))
}
----

Study `src/builtins/nav.js` and `shiki.js` for built-in patterns (options parsing, `resolveSiteAsset`, classifiers, `host.provide` + `host.plugin`), and `apps/mkadoc-plugin-kroki` for the external-plugin pattern (`host.import('zod')`, self-contained package, its own test suite).
