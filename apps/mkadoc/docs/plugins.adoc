= Writing mkadoc plugins

This guide is for authors of mkadoc plugins.
You receive a **plugin host** in each hook — that is the only API you call.
Canonical types live in the `@mkadoc/plugin-host` package (`MkadocPluginHost`, `MkadocPluginFactory`).

Plugins are enabled from config by **locator**:

* `mkadoc:<name>` — built-in factories shipped with mkadoc (allow-listed)
* `file:./path/to/plugin` (or `./path`, absolute paths) — **external** local-folder plugins (installed into `.mkadoc/plugins/` on first use)
* registry specs (`name@range`), `git:…`, `github:user/repo`, `https://…` tarballs — accepted by the config schema, not implemented yet

Use the builtins under `src/builtins/` as reference implementations, and
`apps/mkadoc-plugin-kroki` as the reference *external* plugin.

== What you can extend

[cols="1,3"]
|===
| Extension point | How

| Rendering a markup format | A **renderer** plugin (`kind: 'renderer'`) with `extensions`, `extractMeta`, `render`, `renderFragment` (see <<Renderers>>)
| Renderer-specific document attributes | `addAttributes` in `setup` (e.g. `icons`, `source-highlighter` — consumed by the AsciiDoc renderer; other renderers ignore them)
| Cross-format capabilities | `provideService(name, service)` / `getService(name)` (see <<Services>>)
| Generated CSS / JS on every page | Write files under `host.config.output`, then `contributeHead({ links, scripts })`
| UI below the site topbar | `contributeChromeBody(html)` — HTML appended below the topbar, in plugin load order
| Rebuild sensitivity | `registerSiteWideDep` (rebuild every page), `registerClassifier` (force **full**), or `registerAssetPrefix` (**assets** mode)
| Health checks | `check(host)` → `{ ok, message? }` for `mkadoc check`
| On-disk cache | `cacheDir(name)` under `.mkadoc/`
|===

[[Renderers]]
=== Renderers

A renderer is a plugin with `kind: 'renderer'`:

[source,js]
----
export default function myRenderer(options = {}, host) {
  return {
    name: 'my',
    kind: 'renderer',
    extensions: ['.xyz'],

    // → { title, description, tab } from an index file / frontmatter
    async extractMeta(sourceText, path) { ... },

    // → { html, title, lang, bodyClass, head, assets, includes }
    // html is the article body; core wraps it into the full page.
    async render({ sourceText, absPath, baseDir, attributes }) { ... },

    // render a small markup fragment (used by mkadoc:nav for _nav.adoc files)
    async renderFragment({ sourceText, absPath, baseDir, attributes }) { ... },
  }
}
----

Renderers are auto-loaded (`mkadoc:asciidoc`, `mkadoc:markdown`); listing one
under `plugins:` only passes it options. Core discovers pages by asking each
renderer's `extensions`, dispatches page → renderer, and owns page assembly
(wrapper, theme CSS, chrome, head tags).

[[Services]]
=== Services (provider/consumer)

Cross-cutting capabilities are shared through named services — no dependency
metadata in config:

[source,js]
----
// provider (e.g. mkadoc:shiki)
host.provideService('syntax-highlight', {
  highlight(code, lang) { ... },
})

// consumer (any renderer)
const hl = host.getService('syntax-highlight')
----

* Providers register in `setup`; consumers resolve at *render time*, so load
  order is irrelevant.
* `mkadoc:shiki` provides `syntax-highlight`; renderers consume it for code
  blocks/fences and degrade to plain listings when it is absent.
* `mkadoc-plugin-kroki` provides `diagram`; the `mkadoc:asciidoc` renderer
  consumes its `register` + `attributes` adapter.

== What you cannot extend (core-owned)

* **Topbar / logo / brand** — the topbar is the built-in `mkadoc:topbar` plugin (first in config order so it renders above everything else). Everything below it comes from plugins via `host.contributeChromeBody` (the built-in `mkadoc:nav` is the reference implementation).
* **Page assembly** — core wraps every renderer's article body into the full HTML document (wrapper, default theme CSS, chrome, head tags). Site authors override the *default theme* with `_theme/theme.css`, and *topbar styles* with the first source's `_theme/topbar.css` (mkadoc:topbar appends it after package defaults).
* **Page HTML body** — the article is the owning renderer's output. `contributeChromeBody` is only for shared site UI that appears on every page (for example a left sidebar), not for the article itself.
* **Config schema / CLI / unknown locators** — plugins are registered via known `mkadoc:*` locators or valid package specs (`npm-package-arg` grammar); factory options you validate yourself.
* **Build orchestration** — core decides `full` / `incremental` / `assets` / `noop` and assembles the shared page chrome/head. You only influence rebuilds via `registerSiteWideDep` / `registerClassifier` / `registerAssetPrefix` (see below). You do not take over writing the topbar/header HTML or flushing head tags — use `contributeChromeBody` and `contributeHead` instead.

== Plugin shape

Export a factory: `(options, host) => plugin` (may be async).

Validate `options` in the factory (Zod + `parsePluginOptions`). Reject unknown keys.

Return:

[cols="1,3"]
|===
| Field | Purpose

| `name` | Short id (e.g. `nav`)
| `setup(host)` | Optional. Runs once after the plugin is constructed, **before** rebuild mode is decided. Register extensions, attributes, classifiers, asset prefixes here.
| `contributeChrome(host, ctx)` | Optional. Runs each build after mode is known (not called for `noop`). Emit CSS/JS/HTML. `ctx`: `{ mode, pages, paths }` (`mode` is `full` \| `incremental` \| `assets`).
| `check(host)` | Optional. Used by `mkadoc check` only. Keep it cheap.
|===

Lifecycle order that matters to you:

. Your factory runs (options validated).
. `setup(host)` — classifiers / prefixes must be registered here to affect this build’s mode.
. Core decides `full` / `incremental` / `assets` / `noop`.
. `contributeChrome(host, ctx)` — skipped entirely for `noop`; skip heavy work when `ctx.mode === 'assets'` if you only care about HTML chrome.
. Pages convert with the attributes you registered.

== Plugin host API

Every hook receives the same host object.

=== Context

`host.config`:: Resolved project config (`sources`, `output`, `plugins`, …).
`host.root`:: Absolute project root. Join with relative paths from config.

=== Shared dependencies

`host.import(specifier)`::
Resolve + import a module from **mkadoc's own dependencies** (single shared instance).
Use this for shared libraries instead of declaring them as plugin deps:
`const { z } = await host.import('zod')`. Anchored at mkadoc, so plugins never ship
duplicate copies of shared stateful/stateless libs. Only imports that mkadoc itself
depends on are resolvable.

=== Document attributes

`host.addAttributes(attrs)`::
Merge document attributes applied on every convert (e.g. `source-highlighter`,
`kroki-server-url`, `icons`). These are consumed by the AsciiDoc renderer;
non-AsciiDoc renderers ignore them.

=== Head assets

`host.contributeHead({ links?, scripts? })`::
Queue `<link>` / `<script>` tags that core injects into **every page’s** `<head>`.

* `links` — objects like `{ rel: 'stylesheet', href: '/styles/my.css' }`
* `scripts` — objects like `{ src: '/styles/my.js', defer: true }`

Convention: write the file under `output/` yourself (see `resolveSiteAsset` / `writeIfChanged` in existing builtins), use a **root-absolute** `href`/`src` (e.g. `/styles/nav.css`).

=== Below-topbar chrome

Core always emits:

----
<header id="mkadoc-topbar" class="mkadoc-topbar">…</header>
<!-- plugin chrome fragments follow, in plugin load order -->
----

`host.contributeChromeBody(html)`::
Append a HTML fragment below the topbar. Fragments from multiple plugins are concatenated in **plugin load order** (config key order) — each plugin owns its own element (e.g. `<nav class="mkadoc-sources">`, `<aside id="…">`).

Own your markup and CSS. Typical pattern for a fixed side column (e.g. sidebar):

* Contribute an `<aside id="…">` (stable id).
* Ship CSS that positions it (often `position: fixed`) and adjusts `body` padding with `:has(#your-id)`.
* Do not assume another plugin’s fragment exists unless you document that dependency.

The article itself stays in the normal page body from the owning renderer.
See xref:chrome-design.adoc[Site chrome design] for why.

=== Rebuild hints

When files change under `serve`, core chooses a rebuild mode. These two APIs are how you nudge that choice:

`host.registerSiteWideDep(relPath)`::
“If this path changed, rebuild **every** live page (incremental).”  
Use when your chrome is baked into every page’s HTML (same idea as a virtual include for the whole site). Register in `setup`. Example: `mkadoc:nav` registers each source’s `_nav.adoc` and `_nav.yaml`.

`host.registerClassifier(fn)`::
“If this path changed, rebuild **everything** (true full mode).”  
`fn(relPath)` returns `'full'`, or `null`/`undefined` to leave the decision to core/other plugins.  
Register in `setup`. Prefer `registerSiteWideDep` when reconverting all pages is enough; reserve classifiers for orchestration-level changes.

`host.registerAssetPrefix(prefix)`::
“Changes under this path are **styles/assets only** — don’t reconvert AsciiDoc pages.”  
Pass a repo-relative output prefix (the host normalizes a trailing `/`).  
Example: `mkadoc:shiki` registers the directory of its generated CSS so a CSS-only edit can stay in **assets** mode.

=== Filesystem helpers

`host.ensureDir(relOrAbs)`:: Ensure a directory exists; returns absolute path.
`host.cacheDir(name)`:: Ensure `.mkadoc/<name>/` under the project; returns absolute path.
`host.relToRoot(p)`:: Normalize a path to repo-relative form.

== Conventions

=== Locator and options

* Built-in locators: `mkadoc:<name>` (allow-listed in `src/plugin/locators.js`).
* External locators: `file:./path`, `./path`, or absolute paths — parsed with
  `npm-package-arg` (the same spec grammar pacote/npm use). Relative paths resolve
  against the project root.
* External plugins are installed into `.mkadoc/plugins/<name>/` on first load:
  source is copied (fingerprinted — edits re-copy), runtime deps materialized with
  arborist (`ignoreScripts`, `--omit=dev`, cache under `.mkadoc/cache`), entry
  resolved from `package.json` `main`/`exports` else `index.js`.
* Enable in config as `plugins: { "file:./plugins/you": { … } }`.
* Validate options in the factory; shared libraries come from `host.import`
  (e.g. `zod`) instead of being declared as plugin deps. Do not scrape undeclared
  keys from `host.config.plugins` inside hooks.

=== Assets

* Prefer `/styles/<plugin>.css` (and `.js` if needed) under `output/`.
* Ship plugin assets under your own paths (e.g. `/styles/my.css`); the builtins own `/styles/topbar.*` and `/styles/nav.css`. Site-level topbar CSS tweaks go in the first source’s `_theme/topbar.css` (read by `mkadoc:topbar`).
* Root-absolute URLs in `contributeHead` (leading `/`).

=== Source-tree conventions (site authors)

These are site conventions your plugin may *read*; they are not host APIs:

* First source's `_theme/topbar.css` — optional CSS overrides for **topbar** styles (read by `mkadoc:topbar`; not your job unless you document a parallel file).
* First source's `_theme/nav.css` — optional CSS overrides for **nav/sidebar** styles (read by `mkadoc:nav`).
* First source's `_theme/theme.css` — optional global overrides appended after the default theme.
* Per-source `_nav.adoc` (rich markup) or `_nav.yaml` (declarative) — used by `mkadoc:nav` for link lists. No other nav formats are supported.
+
`_nav.yaml` entries take `label` plus exactly one of `page` (source-relative, normalized to `.html`), `href` (raw), or `children` (nested list):
+
----
- label: Overview
  page: index
- label: Reference
  children:
    - label: Plugins
      page: plugins
----
* Files starting with `_` are partials (not pages). Article `include::` edges are tracked in the core dependency graph (`.mkadoc/deps.json`); editing an included partial rebuilds only the pages that include it. Site-wide deps (`index.*`, logo overrides, `_nav.adoc`/`_nav.yaml` via `registerSiteWideDep`) rebuild every page. `_theme/*.css` is CSS-only (assets mode). An unused partial with no known dependents is **`noop`**. Config still forces a **full** rebuild.

=== `contributeChrome` modes

* `full` / `incremental` — update chrome HTML and CSS as needed.
* `assets` — usually skip HTML chrome regeneration. If your only job is a stylesheet derived from config, you may still rewrite CSS here when appropriate.
* `noop` — core does not call `contributeChrome` (nothing to do).

=== Composition with other plugins

* Chrome-body fragments are concatenated; use distinct element ids/classes.
* Layout conflicts (two plugins both claiming full width under the topbar) are resolved by CSS and documentation, not by the host.
* There is no sidebar-specific host API — only `contributeChromeBody`.

== Minimal sketch
[source,js]
----
export default async function myPlugin(raw = {}, host) {
  const { z } = await host.import('zod')
  const OptionsSchema = z.object({}).strict()
  const options = OptionsSchema.parse(raw)

  return {
    name: 'my',

    async setup(host) {
      host.addAttributes({ 'my-flag': true })
      host.registerSiteWideDep('docs/_my.adoc')
     // or, for true full rebuilds only:
     // host.registerClassifier((p) => (p.endsWith('/_my.adoc') ? 'full' : null))
    },

    async contributeChrome(host, { mode }) {
      if (mode === 'assets') return
      // write /styles/my.css under host.config.output …
      host.contributeHead({ links: [{ rel: 'stylesheet', href: '/styles/my.css' }] })
      host.contributeChromeBody('<aside id="mkadoc-my" class="mkadoc-my">…</aside>')
    },

    async check(host) {
      return { ok: true, message: 'my ok' }
    },
  }
}
----

Study `src/builtins/nav.js` and `shiki.js` for built-in patterns (options parsing, `resolveSiteAsset`, classifiers, extensions), and `apps/mkadoc-plugin-kroki` for the external-plugin pattern (`host.import('zod')`, self-contained package, its own test suite).
