= mkadoc

Write documentation in AsciiDoc and get a static site you can preview locally and publish cleanly.

mkadoc is for people who want:

* docs that stay in AsciiDoc
* a fast edit loop (`serve` with live reload; incremental rebuilds when possible)
* optional extras — sidebar nav, syntax highlighting, diagrams — without leaving the AsciiDoc world
* monorepo-friendly sources (`docs/`, `apps/*/docs`, …) in one site

== Approach

mkadoc treats your project as:

* **Sources** — one or more AsciiDoc trees listed in `sources`, each source is a tab. `index.adoc` is the entry point of each source.
* **Articles** — Asciidoctor convert each `adoc` file to a full HTML page.
* **Output** — HTML under `output` (default `site/`)
* **Plugins** — a plugable way to enrich the default HTML generated by Asciidoctor

These are literately configured by the `[mkdoc-config]` YAML blocks inside `mkadoc.adoc` file.

Some conventions:

* **Config file**: `mkdoc.adoc` under repository root
* **Site root**: `serve` redirects `/` to the *first* source's index page
* **Tab title**: `:tab:` on `{source}/index.adoc`, else doctitle, else last mount segment, else `Docs`
* **Pages**: normal `.adoc` files; names starting with `_` are ignored
* **Cache**: `.cache/` under repository root (not configurable — add it to `.gitignore`)
* **Output**: HTML under `site/` by default, configurable with `output:`

== Get started

From a project with `mkadoc.adoc` and source trees:

[cols="1,3"]
|===
| Command | What it does

| `build` | Full rebuild of all sources.
| `serve` | Full build, watch, serve `output/` with live reload.
| `publish` | Delete `output` + `.cache/`, then full rebuild (for deployment).
| `check` | Verify source dirs and run enabled plugin health checks.
|===

=== Config shape

Typical keys inside `[mkadoc-config]`:

----
sources:
  - docs
  - apps/mkadoc/docs
output: site
plugins: {}
serve:
  remote: false
  port: 8000
----

See the repo-root `mkadoc.adoc` for a full example used by this dotfiles site.

=== Assets

Referenced local files are copied into the output automatically — no config.
During a page build, mkadoc reads the Asciidoctor asset catalog (images, `link:`
targets) plus `video::`/`audio::` blocks, and copies each relative target to the
mirrored path under `output/` (e.g. `docs/images/x.png` → `site/docs/images/x.png`),
skipping unchanged files.

* Relative paths are resolved against the page's source dir; `:imagesdir:` is honored.
* Root-absolute (`/x.png`) and external (`https://…`) targets are left alone.
* `.html`/`.adoc` targets (converted pages / sources) are not copied.
* A missing referenced file logs a warning and the build continues.

Convention: the **first source's `_assets` folder is always copied** to
`<output>/<first source path>/_assets` (e.g. `docs/_assets/` → `site/docs/_assets/`).
Put chrome-level files there (site logo, favicon) and reference them at
`/<first source path>/_assets/…` (e.g. `url('/docs/_assets/logo.png')`); no page
reference is needed. The `_` prefix keeps the folder out of page discovery.

=== Plugins

Enable under `plugins:` with a `mkadoc:*` locator.
For authoring plugins (host API, extension points, conventions), see xref:plugins.adoc[Writing mkadoc plugins].

[cols="1,3"]
|===
| Locator | Role

| `mkadoc:nav` | Left sidebar under the topbar (`#mkadoc-chrome-body`): layout + link styles, panels from each source's `_nav.adoc`.
| `mkadoc:shiki` | Build-time syntax highlighting for `[source]` blocks.
| `mkadoc:kroki-diagram` | Diagram blocks via Kroki (`server_url` required).
|===

Common options (defaults shown):

* `mkadoc:nav` — enable with `{}` (no options)
* `mkadoc:shiki` — `theme: github-light-default`
* `mkadoc:kroki-diagram` — `server_url: …` (required)
