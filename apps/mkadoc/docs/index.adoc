= mkadoc

== Why

Write documentation in AsciiDoc and get a static site you can preview locally and publish cleanly.

mkadoc is for people who want:

* docs that stay in AsciiDoc
* a fast edit loop (`serve` with live reload; incremental rebuilds when possible)
* optional extras — nav chrome, syntax highlighting, diagrams — without leaving the AsciiDoc world
* monorepo-friendly sources (`docs/`, `apps/*/docs`, …) in one site

== How

mkadoc treats your project as:

* **Sources** — one or more AsciiDoc trees listed in `sources`
* **Config** — a literate `mkadoc.adoc` with narrative for people and `[mkadoc-config]` YAML blocks for the tool
* **Output** — HTML under `output` (default `site/`)

Conventions:

* Mount: strip a trailing `docs` segment (`docs` → `/`, `apps/mkadoc/docs` → `/apps/mkadoc`)
* Tab title: `:tab:` on `{source}/index.adoc`, else doctitle, else last mount segment, else `Docs`
* Nav links: optional `{source}/_nav.adoc`; missing → auto page list
* Pages: normal `.adoc` files; names starting with `_` are partials, not site pages
* Cache: always `.cache/` (not configurable — add it to `.gitignore`)
* Output: HTML under `site/` by default (override with `output:`)

Add `.cache/` (and usually `site/`) to your `.gitignore` — both are generated.

Built-in plugins (`mkadoc:*`) opt into features at build time.

Build modes, at a glance:

* **full** — clean slate / publish / config or partial changes
* **incremental** — changed page files only
* **assets** — styles or copied assets only (no page HTML rebuild)

`serve` watches all sources and config, rebuilds, and reloads the browser after a successful build.

== What

=== Get started

From a project with `mkadoc.adoc` and source trees:

[cols="1,3"]
|===
| Command | What it does

| `build` | Convert sources. No paths (or `--full`) → full rebuild. With paths → incremental when possible.
| `serve` | Full build, watch, serve `output/` with live reload.
| `publish` | Delete `output` + `.cache/`, then full rebuild (for deployment).
| `check` | Verify source dirs and run enabled plugin health checks.
|===

=== Config shape

Typical keys inside `[mkadoc-config]`:

----
sources:
  - docs
  - apps/mkadoc/docs
output: site
assets: []   # optional { from, to } recursive dir copies
plugins: {}
serve:
  remote: false
  port: 8000
----

See the repo-root `mkadoc.adoc` for a full example used by this dotfiles site.

=== Plugins

Enable under `plugins:` with a `mkadoc:*` locator.

[cols="1,3"]
|===
| Locator | Role

| `mkadoc:nav` | Section tabs + contextual sidebar from each source's `_nav.adoc`.
| `mkadoc:shiki` | Build-time syntax highlighting for `[source]` blocks.
| `mkadoc:kroki-diagram` | Diagram blocks via Kroki (`server_url` required).
|===

Common options (defaults shown):

* `mkadoc:nav` — `css_href: /styles/nav.css`, `js_href: /styles/nav.js` (enable with `{}`)
* `mkadoc:shiki` — `theme: github-light-default`, `css_href: /styles/shiki.css`
* `mkadoc:kroki-diagram` — `server_url: …` (required)

`css_href` / `js_href` are site-root paths (e.g. `/styles/nav.css`): they set both the HTML link and where the file is written under `output/`.

While `mkadoc serve` is running, changing Shiki theme/langs or enabling/disabling the plugin does **not** require a process restart.
